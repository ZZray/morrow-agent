## 要解决的问题

本地 Codex 等 Agent 掌握源码，需要获取客户现场信息并操作现场环境，完成分析、修复和验证。Reach 提供通用远程能力和组织侧管理服务，既可以与业务产品关联，也可以独立使用。

QSpin 是可选工具来源。LabSlot 是可选管理入口和身份来源。两者均不是远端安装、基础连接或通用工具的硬依赖。

## 用户已确定的行为

| 主题 | 产品要求 |
|---|---|
| 项目归属 | Morrow Agent 仓库的 `apps/reach/` 子项目与业务用例，使用父仓 Git；产品独立部署，通用实现不放入 QSpin 子项目；ARA 仅保留历史来源 |
| 分析入口 | 默认由本地 Agent 结合源码分析；云端提供管理与连接服务。选装 Reach Desk 后，允许云端直接对话及调用 Reach 设备 |
| 控制能力 | 配对后完全控制；不设置 Auto / Full Access 切换、工具权限分层或逐次审批 |
| 登录与配对 | 保留身份识别和配对连接；支持安装后首次配对及再次配对，不建立额外的工具授权中心 |
| 安装 | 双击安装后自动完成安装、注册系统服务、加入 PATH、启动服务并退出安装器 |
| 模型 | 客户无需配置模型；远端需要模型推理时使用组织提供的服务 |
| 平台 | Windows 优先，Mac/Linux 后续 |
| 通用桌面能力 | 优先接入现有开源 Computer Use 实现 |
| 产品绑定 | 可以不关联任何产品，也可以接入一个或多个产品能力 |
| 系统集成 | 首版作为独立 Reach 应用部署到 Ray 工作台服务器，在工作台增加入口；LabSlot 集成延期 |
| Reach Desk | 作为 Reach 的可选云端对话扩展；默认不集成，Ray 可以选装。基础连接、被控端、配对和操作记录归 Reach |

完全控制描述配对后的产品行为，具体操作仍通过实际操作系统会话和工具接口执行。Windows 服务安装可能触发系统自身的 UAC；不因此增加产品引导页、权限模式或功能审批步骤。

安装、配对和运行记录应清楚显示真实状态。取消、断线或结果未知不能被记录成执行成功，也不能通过自动重放动作掩盖状态。

## 当前架构建议

以下是待评审的组织方式，不是已经实现或全部定案的架构：

- `service`：注册、配对、连接中转、任务事件和收据；需要时接入组织模型服务。
- `node`：客户机 Host、系统服务、工具后端及按需桌面会话接入。
- `controller`：提供本地 MCP 和 CLI，两种入口共享连接逻辑。
- `admin`：Agent、连接、配对和运行记录页面，可由外部系统挂载。
- 可选 `Reach Desk` 扩展：云端聊天界面、对话历史及云端 Agent Host；通过 Reach 的公共控制合同调用设备，不再独立管理设备连接。

本地 Agent 可以逐次调用远端工具，也可以委托远端完成子任务。需要远端循环时复用 ARA Lite Core 与 Harness；远端循环的位置和模型推理服务的位置分别描述。

当前部署面向 Ray 工作台，Reach 持有自身账户、数据和服务生命周期，已通过服务端身份桥接复用 Ray 登录。首版不接 LabSlot。云端平台扩展仍在设计，Ray 可以选择启用；默认发行不加载聊天路由、聊天资源、云端模型进程或聊天数据存储，也不要求模型配置。

启用扩展后，可以不连接设备而直接与云端模型对话，也可以明确选择已配对的 Reach 设备执行任务。扩展范围和旧 HandWave 迁移条件见[扩展设计](platform-extension.md)。此处的选择用于确定执行位置，不是权限模式。

产品可以调用同一基础安装包并登记自己的能力配置。共享 Agent 的更新及卸载归属、产品卸载后的处理，需要在安装设计中确定。
