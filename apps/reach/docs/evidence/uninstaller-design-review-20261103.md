## 本次采用的方案

采用主设计提出的更简单方案：**Windows 应用列表通过系统 Windows PowerShell 调用受保护的外部卸载脚本；下载版 Setup 提供 `--uninstall`，使用同一份嵌入逻辑。** 不新增独立 `uninstall.exe` 或第二个 Rust crate。程序文件删除后，保留原程序根目录中的事务锁、明确的未安装记录和收据；它们是有意保留的元数据，不能报告为“整个根目录已删除”。

该方案消除了必须删除正在运行的卸载 EXE 的问题。PowerShell 进程映像属于 Windows，外层等待提权内层完成不会锁住待删程序目录。按下述身份、锁顺序、恢复入口和终态约束实现，可以接受为本执行点的实现设计；这不接受真实卸载能力或整体验收。

这是实现选择，不新增产品审批或额外引导步骤。I01 要求卸载资源与入口，没有要求必须有一个独立卸载 EXE。

## 当前源码依据与最初方案的问题

复核基线为现有完整候选代码：

| 文件 | SHA256 |
|---|---|
| `packaging/windows/install.ps1` | `156157eb53206a01b4dd305966409fb6e0a725dc6daeaba00043723c510e4284` |
| `packaging/windows/setup/src/main.rs` | `f077e082abad1c5aa6848e863c9e478c1acf28b7ca7f22d5dafc2bf2624e28e8` |

- setup 的 `elevate` 等待提权子进程退出（52–79 行）；`run_powershell` 通过 `wait_with_output` 等待系统 PowerShell。若独立卸载 EXE 照搬这两个等待，再让清理进程等原 EXE 退出，会形成互相等待。采用系统 PowerShell 入口后不需要这套 ready/退出交接协议。
- 安装锁目前是程序根目录的 `install.lock`，以 `FileShare.None` 打开（install.ps1:105–110）。它明确不允许持有期间删除或替换。不能一边保持旧版互斥，一边声称已删整个根目录；关闭旧锁后再递归删除根目录又会引入旧安装器插入重装的竞态。保留根目录和原锁避免了这个问题。
- 安装脚本的 `RecoverJournal` 只接受安装操作及固定 schema/phase（307–311 行）；旧版不会理解新的卸载状态。新版本必须显式分派安装、卸载和未安装记录，不能把卸载 journal 交给旧安装回滚函数。
- `maintenance-stop` 要求无 pending pair、无 active/outbox，配对后还查询远端 pending（windows_host.rs:319–337）。它适用于升级的停领门槛，不能机械地成为卸载前置，否则离线或保留未上传收据的机器无法卸载。

以上是现有源码事实。下面是待落实的设计，不能引用为已执行证据。

## 两个入口与一个执行主体

### Windows 应用列表

使用 64 位 HKLM Uninstall 自有子键，注册指向**系统 Windows PowerShell 的绝对路径**。命令中的短固定 bootstrap 只负责管理员检查、必要的系统 UAC、完整加载受保护脚本和返回最终结果。不得依赖 PATH 查找 `powershell.exe`，也不能执行用户临时目录里的脚本。

推荐 bootstrap 先完成 UAC，再调用 `ReadAllText`，由 `ScriptBlock.Create` 执行完整内容。这样文件读取结束时句柄已经关闭，不依赖 `-File` 对脚本文件句柄寿命的隐含假设。短 bootstrap 可以编码传递，路径由系统已知目录和固定产品名称产生，不把 journal 字符串拼成任意命令。

将 UAC 放在 bootstrap 可避免另一项不必要的改造：当前 `%ProgramData%/RY` 是受保护数据父目录，不应为了让普通用户先读脚本而放宽共享父目录、账本或 spool 的权限。提权后的脚本仍须断言管理员 token。

脚本位置采用 `%ProgramData%/RY/Reach.maintenance/uninstall.ps1`。安装时必须校验父路径的 Owner/DACL/reparse，按可信代码的要求建立该目录和文件，记录脚本摘要。正常用户只能通过固定入口请求系统提权，不能替换其中的脚本或参数。共享 `RY` 父目录仅按合同验证，不重写其他产品的 ACL。

普通用户取消 UAC时没有进入卸载事务，也没有停止服务或修改 PATH。管理员直接进入同一事务；标准用户输入另一管理员凭据时，授权 token 与原绑定用户 SID 分开记录，不将管理员 SID 写回配对归属。

### 下载版 Setup `--uninstall`

下载版 Setup 复用现有系统 UAC 和私有 stdin 传输，执行同源的嵌入卸载脚本。它读取可信现有安装身份，不使用启动者当前 SID 代替原绑定 SID，不使用下载包中 Node 的 SHA 冒充当前安装的目标身份。下载副本自身不在清理范围内，卸载不会删除它。

此路径无需依赖已安装的卸载脚本仍存在，因此可用于脚本丢失、最终收尾中断和从下载目录重试。必须校验所理解的安装/journal schema；版本过旧时明确拒绝，不能猜测新记录。

若用户把 Setup 本身放进了本次待删程序子树，同步等待子脚本就可能阻碍删除。应检查当前映像的真实位置/身份，明确拒绝这个异常执行位置或转入系统 PowerShell 入口；不能靠超时重试删除自己，也不能扫描同名进程后全部终止。正常下载目录不受此限制。

### 成功的来源

两个入口都能等待实际系统清理进程结束，**不把“已启动子进程”或启动器退出 0 当成卸载成功**。返回成功须同时满足下文的后置条件、同一事务的 committed journal 和最终退出结果。失败只显示一次实际错误及可恢复事务；不增加“下一步/完成”向导。

## 锁、身份与旧版隔离

新安装、更新、卸载和恢复统一采用以下顺序：

1. 验证系统锚点及受保护 `RY` 数据父目录。
2. 获取 `%ProgramData%/RY/Reach.installation.lock`。
3. 若程序根目录存在，获取原 `root/install.lock`；新安装创建根目录后也按同一顺序取得它。
4. 在两锁内读取/恢复 journal、校验安装身份，之后才创建程序子目录、修改服务、PATH、注册或发布文件。

两把锁均为受保护的持久文件，`FileShare.None`，持有期间不删除、不替换；卸载正常完成后也保留。新代码不得出现 legacy→external 的反向获取。等待应有界并报告 busy，不长时间持第一把锁无限等待第二把。

保留 legacy 锁不是多余残留：旧安装器只认识它，必须让它一直阻止旧版与新卸载交错。旧版在获取锁前可能创建空 `bin/versions` 目录；这不是程序仍安装的证据，新流程不能为清除空目录而解除锁并递归删除整个根目录。

在第一次服务或文件副作用前，必须持久化**旧安装器明确不支持的卸载计划**：根目录的 `install-journal.json` 使用 schema 3、operation=uninstall。这一份记录同时是唯一事务权威和旧版屏障。不能只在旧 schema 里加一个可能被旧代码忽略的 `status=uninstalled` 字段。结束时 `install.json` 也使用新 schema 的明确 uninstalled 记录。

既然程序根目录和旧锁明确保留，就不再新增外部 journal；外部仅保留共用锁与尚在工作的维护脚本。计划一次落盘即建立屏障，消除了两份 journal 的同步窗口。计划持久化前没有不可逆副作用；重试须对照原 manifest/journal 身份，若旧安装器已经改动它们则拒绝续用旧计划。唯一 journal 缺失或损坏时应停在可诊断状态，不猜测“已完成”或恢复旧程序。

目标身份至少包含绑定 SID、保留的 installationId、根目录/服务精确路径、部署身份、原安装记录摘要及目标文件范围。**部署身份要独立于 installationId**：重装按合同保留 installationId，同一包也能重装，不能用它或 Node SHA 判断是否仍为原一代。新安装每次成功部署生成新的 generation；卸载 journal 和 Uninstall 注册均绑定该 generation。旧 journal 不得删除已重装的新一代，即使路径和包 SHA 相同。

新安装器见到未完成卸载时先续办或明确报告该事务，不进入普通安装/旧版 rollback；见到可信 uninstalled 终态后，沿用 `%ProgramData%/RY/Reach.installation.json` 的 SID/installationId，再建立新 deployment generation。未知 schema 或身份不一致必须拒绝。

## 服务、程序和 PATH 的删除边界

**服务。** 只操作可信安装记录对应的 `RYReach`。服务名、显示名或同名 EXE 都不能单独证明归属；必须比较实际 SCM 配置、精确安装路径和运行进程映像，持有真实进程句柄后再停止。同名第三方服务、无可信记录的服务或外部更改的配置均拒绝，不停止、不重配、不删除。

卸载采用本地 SCM stop 的停领/结束工作进程/保留 unknown 与 outbox 的已有合同；不要求远端在线，也不要求为了卸载先上传所有收据。已停止服务不为索取维护 ACK 而启动。停止后同时确认 SCM 状态及原进程退出；不能仅凭当前 PID 不见、SCM stopped 或等待固定秒数判断原进程和工作树已经结算。超时不删除正在使用的程序。

需要禁用自启动或恢复启动策略时，先记录原配置与变更意图，再修改。失败后不得无条件重启可能已经部分删除的程序。卸载进入不可逆删除后采用向前重试，不套用安装器“恢复旧包”的流程。

`DeleteService` 成功只说明请求删除。必须关闭自持的 ServiceController/SCM 服务句柄，再确认服务确实不存在；只能把明确的 1060 视为不存在。Access denied、SCM 查询失败和标记删除但仍可见都不是成功。第三方管理器持有句柄导致删除未完成时，保留脚本、注册和 journal，报告可重试状态，不用重启删除冒充当前删除。

**程序。** 清理目标来自可信根目录和明确的自有程序范围，包括 CLI、所有自有版本、桌面 helper/Python/配置及本产品安装资源。缺失或损坏程序不能仅因不能通过“健康可启动版本”校验而永久无法卸载；身份/归属校验与完整运行校验分开。任何递归操作前都要核定最终绝对路径仍在允许范围，校验 reparse，使用原生 PowerShell 的 LiteralPath，不跨 shell 拼接删除。

根目录的允许保留集合为原 `install.lock`、新 schema 的 uninstalled 安装记录、卸载屏障/收据等明确元数据；没有保留程序即可以完成程序移除。未知根目录内容、路径逃逸或不可信链接应留下并准确报告，不能扩大删除范围又声称正常干净卸载。

**数据。** 默认保留整个 `%ProgramData%/RY/Reach` 账本及 WAL/SHM、配对与未上传收据，保留旁置 `Reach.installation.json`，也保留 `ReachDesktop` 每代 spool。windows_desktop.rs:298–312 明确 spool 位于独立目录，不能误认为它随程序树一起删除。活动服务停止可能新增真实 unknown/收据；这不等于允许回滚账本或丢弃收据。此执行点不加入永久清除数据选项。

**PATH。** 只有已确认归属才删除。沿用原 `pathOwnership` 的完整原文、RegistryValueKind、applied 证据：当前值仍等于本产品确认写入值时可恢复原值；已经等于原值时按幂等结果处理。值缺失、类型异常、写入归属未知或其他程序改过 PATH 时，不能仅搜索相同路径文本并删掉它。保留当前值并记录 `ownership_uncertain_preserved`；这可以作为明确的保留项，不伪装成已删除。确认属于本产品但实际写入失败时，保持可重试失败。写入前再次校验当前原文，保留其他条目和类型，并通知环境变化。

## 可重试状态机

以下阶段名称是建议枚举，实际实现可合并，但不能合并事实边界。每个有副作用的步骤先写意图，步骤完成后记录已观察结果；journal 原子替换并实际 flush，不以内存变量作为恢复依据。

| 阶段 | 必须已固定/观察的事实 | 中断后动作 |
|---|---|---|
| `prepared` | 目标 generation、身份、原服务/PATH/注册、脚本摘要、删除/保留范围，旧版屏障已成立 | 重核同一目标；没有副作用时不能跳到成功 |
| `stopping` | 已记录原服务和实际进程身份，停止意图先落盘 | 核对当前服务归属；继续等待/停止同一目标，不按裸 PID 杀进程 |
| `stopped` | SCM stopped，原进程及工作树按合同结算，收据保留 | 不重新启动；继续服务删除 |
| `service_removing` | 删除意图已落盘 | 查询真实不存在；标记删除/访问失败继续 pending |
| `files_removing` | 服务已不存在，程序删除范围固定 | 重做剩余自有文件删除；缺失即幂等，替换成新一代则拒绝 |
| `program_removed` | 程序目标已删除，保留集合清楚，PATH 已删除/已无/明确保留 | 固定 uninstalled tombstone 和待提交收据；继续注册清理 |
| `registration_removing` | 核定自有 Uninstall key 和 generation，仍有完整外部脚本 | 删除且核验本键不存在，不能删同名但不同归属的键 |
| `entry_cleanup` | Uninstall 注册确实已移除 | 删除已完整读入的外部脚本及空 maintenance 程序目录；保留外部锁和根目录 journal |
| `committed` | 服务无、程序无、注册无、卸载脚本无、PATH disposition 已定、保留数据与元数据明确 | 返回真实成功；重试只复核结果，不重新停止/删除新一代 |

在 `program_removed` 到最后 committed 之间，根目录收据若提前写入应声明 `requiresCommittedJournal`，必须与根目录实际持久化的同一 txId/generation 的 committed journal 合看。看到“程序没了”、内存中的 phase 或某一个结果文件，不足以宣布事务完成。阶段写入失败不得留下内存已推进的假象，返回终态前须重新读取真实 journal 与收据核对。

Uninstall 注册与文件系统/JSON 无法形成一个原子事务，因此必须定义两种恢复窗口：

- **注册尚存在的失败阶段：** 外部脚本仍保留，应用列表可以再次进入同一逻辑。不得先删脚本再试图删除注册。删除注册失败时必须保留可读取的完整脚本。
- **注册已删除之后：** 程序主体已经移除；若脚本删除或最终 journal 写入失败，应用列表入口已无，使用下载 Setup `--uninstall` 或新安装器的卸载恢复分支继续。记录实际 `entry_cleanup`/收尾状态，不假称 OS 入口仍然存在，也不回建一个指向缺失文件的注册项。

这就是最后窗口的明确恢复入口。无需为了关闭该窗口引入常驻恢复 EXE、计划任务、重启删除队列或保留第二套 Agent；它们会增加新的生命周期，而不能使 registry 与文件系统变成同一事务。

## 安装侧必须一起变更

新卸载入口不是单独加一个脚本即可交付。安装侧至少要同步：

1. external→legacy 锁顺序及取得外部锁的时机；外部锁在任何程序/服务/注册变更前。
2. 新 schema/operation/generation 和卸载恢复分派；uninstalled tombstone 的重装路径。
3. 受保护 maintenance 脚本的安装、摘要和旧内容恢复；Uninstall 注册的精确所有权、64 位视图、完整命令引号及 schema/version。
4. 将脚本/注册发布纳入安装事务：安装失败时只恢复自己实际改变且当前仍符合本事务身份的内容，不覆盖第三方修改。必须先写脚本并验证，再公布应用列表入口。
5. 下载 Setup `--uninstall` 与落地脚本共用同一源文件和合同；不能维护两套行为逐渐分叉的卸载实现。

既有共享基础包与可选产品共存合同仍然成立：解除某个可选产品不应调用基础卸载，活跃产品引用不能被当成无关联忽略。本设计不把尚未实现的产品引用登记说成已经验收。

## 后续验证清单与接受范围

普通用户的机制测试可以先完成，但生产验证须另记，不可合并计数：

- 实际 Windows PowerShell 5.1 读入脚本后删除脚本文件，外层系统 PS 等内层退出；下载 Setup 在目录外同步等待；没有启动即成功或自等死锁。
- 新安装/卸载争锁、两锁顺序、旧安装器持 legacy 锁、旧固定代码读取新卸载屏障后拒绝、重装同包使用新 generation，原 SID/installationId 继续保留。
- 对每个 journal 写入和副作用边界注入中断，尤其服务标记删除、部分文件删除、PATH 写后未记结果、注册删除后、脚本删除后、最终 committed 写入失败；恢复不能重做已发生业务动作。
- 服务未运行、已不存在、离线且有 outbox、同名第三方服务、映像不匹配、PID 复用、原进程不退出、外部服务句柄未关闭；错误不能被当成不存在。
- PATH 无归属、原值已经恢复、并发新增/修改、重复或不同大小写文本、不同 RegistryValueKind、写入失败；不误删其他产品条目。
- 脚本/祖先 Owner 或 DACL 不可信、reparse、Unicode/空格路径、脚本损坏/缺失、未知记录 schema、陌生注册键和未知根目录文件；失败有具体范围。
- 真实普通用户 UAC、管理员入口、取消 UAC、另一管理员凭据、Windows 应用列表和下载目录重试；真实 SCM/SYSTEM/WTS/工作树结算及重装后的身份与数据保持。
- 真实程序及脚本删除后核对没有可执行载荷遗留，明确列出保留的 root/lock/tombstone、账本和 spool；不使用延迟到重启删除作为已删除证据。
