error[vulnerability]: Buffered application data sent to outer server after ECH rejection
   ┌─ E:\repos\ara\apps\reach/Cargo.lock:77:1
   │
77 │ rustls 0.23.45 registry+https://github.com/rust-lang/crates.io-index
   │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ security vulnerability detected
   │
   ├ ID: RUSTSEC-2026-0347
   ├ Advisory: https://rustsec.org/advisories/RUSTSEC-2026-0347
   ├ When a server rejects Encrypted Client Hello (ECH), the client completes the
     handshake using the outer ClientHello and authenticates the server against the
     ECH config's `public_name`. At the end of that handshake, rustls encrypted and
     queued any application data buffered via `ClientConnection::writer()` *before*
     queueing the `ech_required` alert.
     
     The application correctly receives
     `Error::PeerIncompatible(ServerRejectedEncryptedClientHello)`, but the next
     `write_tls()` call (needed to send the alert) also sends the buffered
     application data. Plaintext meant for the inner server therefore goes to the
     client-facing server named by `public_name`.
     
     That server is authenticated, so this is not exploitable by an unauthenticated
     party, but it violates RFC 9849 section 6.1.6, which requires the client to
     abort with `ech_required` "before sending any application data to the server".
     
     This affects only clients that:
     
     - use `EchMode::Enable` (GREASE ECH is not affected),
     - write application data before the handshake completes, and
     - connect to a server that rejects their ECH config (for example, because it is stale).
     
     The underlying ordering bug is older, but before 0.23.44 the client checked
     the server certificate against the inner server name rather than `public_name`,
     so certificate verification failed first and no data was sent.
   ├ Announcement: https://github.com/rustls/rustls/pull/3300
   ├ Solution: Upgrade to >=0.23.46 (try `cargo update -p rustls`)

error[vulnerability]: Unauthenticated ServerHello can downgrade later connections to classical key exchange
   ┌─ E:\repos\ara\apps\reach/Cargo.lock:77:1
   │
77 │ rustls 0.23.45 registry+https://github.com/rust-lang/crates.io-index
   │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ security vulnerability detected
   │
   ├ ID: RUSTSEC-2026-0349
   ├ Advisory: https://rustsec.org/advisories/RUSTSEC-2026-0349
   ├ The client recorded the server-selected key exchange group for each server
     name when processing the ServerHello, before the server was authenticated.
     This record is used to predict which key share to send in future ClientHellos
     to that server name.
     
     A network attacker can answer one connection attempt with a ServerHello
     selecting X25519, and then close the connection. Later ClientHellos for that
     name carry only an X25519 key share, while `supported_groups` still lists
     X25519MLKEM768 first. If the genuine server accepts that share rather than
     sending a HelloRetryRequest for its preferred hybrid group, the handshake
     completes with classical-only key exchange and no error. This persists for as
     long as the entry stays in the client's session store.
     
     The impact is loss of post-quantum confidentiality for affected connections
     ("harvest now, decrypt later"). There is no key compromise and no
     authentication bypass.
     
     The following are not affected:
     
     - connections to servers which send a HelloRetryRequest for their preferred group,
     - clients with resumption disabled (as nothing is stored), and
     - other server names.
     
     This behaviour is discussed in
     [draft-ietf-tls-key-share-prediction](https://www.ietf.org/archive/id/draft-ietf-tls-key-share-prediction-01.html#name-security-considerations),
     so the practical impact depends largely on server policy.
   ├ Announcement: https://github.com/rustls/rustls/pull/3355
   ├ Solution: Upgrade to >=0.23.46 (try `cargo update -p rustls`)

    ┌─ E:\repos\ara\apps\reach/Cargo.lock:101:1
    │
101 │ tokio 1.53.1 registry+https://github.com/rust-lang/crates.io-index
    │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ unsound advisory detected
    │
    ├ ID: RUSTSEC-2026-0386
    ├ Advisory: https://rustsec.org/advisories/RUSTSEC-2026-0386
    ├ `tokio::io::unix::AsyncFd` provides safe constructors (`new`, `with_interest`, `try_new`, and `try_with_interest`) that accept any `T: AsRawFd` rather than requiring proof of ownership or validity of the file descriptor. Because `RawFd` implements `AsRawFd`, safe code can construct an `AsyncFd` from an arbitrary or closed file descriptor, or close/replace the underlying file descriptor while the `AsyncFd` is still alive.
      
      This violates I/O safety in two ways:
      
      1. `AsyncFd<T>` implements `AsFd` for all `T: AsRawFd` by calling `BorrowedFd::borrow_raw(self.as_raw_fd())`, allowing safe code to obtain an arbitrary `BorrowedFd<'_>` without owning the file descriptor.
      2. Tokio's I/O driver stores a pointer to an internal allocation in the `epoll`/`kqueue` user data for registered file descriptors. If the underlying file descriptor is duplicated and then closed while an `AsyncFd` is alive, and the OS reuses that file descriptor number for a another IO resource on the same runtime, dropping the first `AsyncFd` deregisters the reused file descriptor number and frees the first while the original file description remains registered in `epoll`, leading to a use-after-free when a readiness event fires.
      
      Starting in Tokio 1.51.6, 1.53.3, and 1.54.0, `AsyncFd::new`, `AsyncFd::with_interest`, `AsyncFd::try_new`, and `AsyncFd::try_with_interest` are deprecated in favor of the `unsafe` constructors `AsyncFd::register` and `AsyncFd::register_with_interest`. Callers must ensure that the file descriptor remains valid, open, and unchanged for the lifetime of the `AsyncFd`.
    ├ Announcement: https://github.com/tokio-rs/tokio/pull/8587
    ├ Solution: Upgrade to >=1.51.6, <1.52.0 OR >=1.53.3 (try `cargo update -p tokio`)
