## 目标与完成标准

Reach 为本地 Codex 等 Agent 提供通用远程操作能力。本地结合源码分析，远端执行系统、桌面和产品工具；组织侧提供连接、管理和按需模型服务。

首版建议以 Windows 内测版本为交付目标，暂称 v0.1。版本号、具体技术栈和支持环境在 P0 明确。本计划拆为 8 个阶段、52 项任务；目前功能验收为 **0/52**。项目骨架和本文档不计入功能交付。

另设 5 项 Reach Desk 选装任务（0/5）：云端直接对话、Reach 设备调用及旧产品迁移。默认 Reach 的交付不依赖这组任务；Ray 选装组合需另外完成其验收。具体设计见[云端平台扩展](platform-extension.md)。

## 组件与安装组成

下列是源码职责建议，进程数量、语言和构建方式由 D01/D02 确定。

| 组件目录 | 部署位置 | 职责 | 数据与依赖边界 |
|---|---|---|---|
| service | 组织服务器 | 安装登记、身份与配对、连接中转、任务事件和收据；接入组织模型配置。 | Reach 维护自身身份与运行数据，外部资产只保存来源引用。 |
| node | 被操作的 Windows 机器 | 系统服务、工具宿主、按需交互会话助手、远端 Lite/Harness Host。 | 保存安装身份及执行现场；用户无需配置模型或开发环境。 |
| controller | 开发者本机 | reach CLI 与供 Codex 使用的 MCP，共享目标选择、连接和结果读取。 | 本地 Agent 读取源码并判断整体任务；命令与 MCP 共用合同。 |
| admin | 组织 Web 服务 | Agent、连接、配对、运行记录及证据页面。 | 默认保持管理职责；Ray 工作台进入时复用平台登录。 |
| platform / Reach Desk（选装） | 组织云端 | 直接对话、会话历史、云端 Lite/Harness Host，通过 Reach 调用设备。 | 默认不安装或加载；会话数据归扩展，设备/配对/操作归 Reach。 |

被操作机器的安装包包含 Node、所需运行时、工具后端、桌面会话助手及配对 CLI。CLI 在目标机负责配对/状态，在开发机承担控制入口；二者如何共用或分发由 D02/D05 决定。开发者侧安装 controller 并接入 Codex MCP；组织侧部署 service 和 admin，配置登录来源及模型服务。

产品安装器可调用同一 Reach 基础包，随后登记自己的能力配置。未登记产品也能使用。多个产品共享安装时，更新和卸载必须遵循同一合同。

## 用户流程

1. 在 Ray 工作台服务器部署独立 Reach 服务与管理页面，工作台增加入口并复用 Ray 登录；独立部署及原生客户端保留自身认证。
2. 用户双击 Windows 安装器，自动安装组件、注册服务、加入 PATH、启动服务并退出。Windows 自身 UAC 与产品安装步骤分别说明。
3. 从管理入口取得配对信息，在目标机使用 reach 命令完成首次配对。服务地址定位、配对码有效期及多控制端关系在 D03 明确。
4. 本地 Codex 通过 controller 选择目标，直接调用远端文件、命令、进程、日志、桌面或已接入的产品工具。
5. 需要连续现场取证时，Codex 提交子任务；远端复用 Lite/Harness 和组织模型执行，返回状态、结果与证据，本地结合源码判断。
6. 断线后读取原操作收据；效果未知时保留未知状态。再次配对、替换连接或解绑无需重新安装。
7. 管理页面用于查看 Agent、配对、连接及运行记录；Ray 浏览器单次登录已接通，完整管理能力仍按清单验收。
8. 可选安装 云端平台扩展后，用户可在云端直接聊天；需要现场操作时选择 Reach 设备，结果回到同一操作账本。默认 Reach 不出现或加载这条对话入口。

配对后采用完全控制，不增加工具权限模式或逐次操作审批。首版能力矩阵用于标明已经实现和验收的工具，不能成为运行时权限白名单。系统会话或后端的实际限制必须如实返回。

## 第一步具体做什么

P0 从 D01 开始：画清本地 Codex、controller、service、node、admin、组织模型和产品工具的调用关系，确定每类数据的所有者。随后 D02 对固定来源版本调查复用边界和构建成本；D03 同步补齐独立登录与配对流程。

D04–D07 将工具、安装、桌面后端和外部接入变成可实施合同。D08 汇总验收矩阵并估算工作量。P0 完成时应能逐项回答：要改哪里、复用什么、输出什么、怎样证明有效。

## 任务完成与文档更新流程

1. 开始任务前检查依赖，标记状态、负责人和目标版本；引用对应产品决定与设计合同。
2. 补齐设计后实施最小完整改动；差异影响已确定合同的，在对应文档记录原因。
3. 在交付版本执行任务验收，保存环境、操作、实际结果和未覆盖项。代码检查、受控替身、真实进程、真实桌面、真实模型及硬件证据分别标注。
4. 独立复核结果，修正问题后才在任务清单勾选完成。Run 成功、文档完成、HTTP 成功或服务在线均不自动代表业务验收通过。
5. 同步受影响的专项文档、索引和知识来源；用户行为发生更正时优先更新范围及来源记录。

项目负责人/作者标识为 Ray Zhang；具体实施者和独立复核者在任务启动时填写，当前不虚构人员分工。跨仓库工作记录各自版本和负责人，保持 Reach 核心独立。
